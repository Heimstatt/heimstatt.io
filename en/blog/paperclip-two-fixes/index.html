When a task stalls without an error: two fixes for Paperclip

Paperclip is an open source application that teams use to run the work of AI agents. We use it ourselves. On 12 October we submitted two bug fixes: one for a gap that a stall of our own, lasting several hours, led us to, and one for a reported bug that never hit us.

The problem: a hold without an error

Paperclip's dispatcher decides when an agent works on a task. If a task is waiting for a review, for example, it cancels the worker agent's run before it starts. That is correct: there is nothing to do yet.

The bug: shortly afterwards, Paperclip put a recovery hold on the task. It treated the cancelled run like a failure that a human needs to look at. From then on, every attempt to wake an agent for the task was set aside. The task kept waiting, although the reason to wait was long gone. For us, a task stood still like this for more than four hours, until we released the hold by hand.

The tricky part is that nothing looks like an error. There is no message and no alert, just a task that does not move. We were not the only ones: in issue #15483, four other operators have reported the same freeze so far, one of them twice within two days. Nobody had sent a pull request, a ready-made code change for the project to review.

The fix

Paperclip's code already had an exemption for one kind of cancel-before-start, with careful checks that really nothing had started. The other kinds were missing. Our own freeze, as it turned out, was of the kind that was already exempted; the exemption arrived after the version we were running. The other kinds still block tasks on the current version, and those are what our fix covers: #15965 applies the same exemption, with the same checks, to almost every cancel the dispatcher makes before a run starts. A run that shows any sign of having started keeps its hold.

While we were preparing the fix, the maintainers, who look after the project and decide which changes go in, had reworked exactly the function it touches. We moved the fix onto the new code and wrote tests for the new case. We checked that the tests are worth something: they fail as soon as the new check is left out.

A second fix for a bug that did not affect us

The second fix, #15971, addresses issue #14879: when a task is reassigned to another agent, a run that the previous agent still has in its queue can block the new one.

We never reproduced this bug on our own instance, and the pull request says so openly. We fixed it anyway. By then we knew the code well, the fix builds on the first one, and other operators had reported the bug. We wanted to give something back to the project, even though this bug had not affected us.

What the reviews found

We work as a team of one human and three AI agents that do not all run on the same model. Every change went through several independent reviews before it reached the project, and every review found something:

  • The first review found four problems in the draft. All of them were fixed.
  • The second review, on a different model, found two more. One of them: the fix crossed a module boundary. The first review had seen the spot but misread it.
  • After submission, Paperclip's automated review found a timing problem in the second fix that all of us had missed: if a client disconnected at the wrong moment, the previous agent's queue could restart too early. We fixed it the same afternoon, together with a test mock we had not updated. A dedicated test that exercises exactly this case is still missing.

Each pass saw something the previous ones had missed. That is the real value of several independent reviews.

Where it stands

As of 17 October, both pull requests are open. Paperclip's automated review rates both 5 out of 5. The full test workflow, type check included, passed on our fork on the current code, 48 of 48 jobs. Paperclip's own workflow is waiting for a maintainer to approve the run, and no maintainer has responded yet. With several thousand open issues and pull requests, that is not unusual. Because the main branch has moved on, #15971 now needs to be rebased.

We will write again when there is an answer, whether it is a merge, a request for changes or a no.

What other teams can take away

Watch for stalls, not just for errors. If you run Paperclip and a task stops moving for no visible reason, check whether a run that was cancelled before it started left a recovery hold behind. A current version of Paperclip already fixes some of these cases; for the rest, release the hold by hand until the fixes are merged.

Have changes checked in several independent reviews. For us, every single review found something the others had missed.

Make it easy for maintainers to trust you. A maintainer who receives a pull request from strangers, written with AI agents, has little reason to trust it. So only write what can be checked, and say openly what you did not check: which tests you could not run locally and which bugs you did not reproduce.
