Read before running: how we use other people's agent skills

If you work with an AI agent, sooner or later someone will recommend a skill. A skill is a small folder with instructions that teaches an agent one kind of task: writing release notes, reviewing a contract, drawing a diagram. There are public directories with thousands of them, and installing one usually takes a single command.

Our team uses skills every day. Almost all of them we wrote ourselves. When we find a good skill from someone else, we read it, take the idea and write our own, smaller version. This post explains why, what the current debate about skills being already obsolete actually says, and what you can check before you install the next one.

What a skill is

The format comes from Anthropic, the company that makes the Claude models. In October 2025 it described Agent Skills: "At its simplest, a skill is a directory that contains a SKILL.md file. This file must start with YAML frontmatter that contains some required metadata: name and description."

An agent loads only the name and description of every skill at the start. It reads the full file when the task calls for it, and further files in the folder only when it needs them. In December 2025 the format became an open specification. Its overview page lists dozens of tools that read it, among them OpenAI's Codex, GitHub Copilot, Cursor and Google's Gemini CLI. A skill written once can be used in many of them.

The important word in that description is "folder". A skill can carry more than text. It can bring scripts that the agent runs on your machine, with your files and your access.

Why we do not install skills blind

Snyk, a security company that checks software for vulnerabilities, scanned 3,984 skills from two public directories, ClawHub and skills.sh, in February 2026. In their words: "13.4% of all skills, or 534 in total, all contain at least one critical-level security issue". They confirmed 76 malicious payloads, built to steal credentials, install backdoors or send data away.

A larger study by eight researchers, published on arXiv (a server where researchers share papers before peer review), analysed 31,132 skills and found at least one vulnerability in 26.1% of them. One finding matters for anyone choosing a skill: "skills bundling executable scripts are 2.12x more likely to contain vulnerabilities than instruction-only skills."

Anthropic, which invented the format, says the same in the article that introduced it: "We recommend installing skills only from trusted sources." And: "When installing a skill from a less-trusted source, thoroughly audit it before use." Its advice is to start by reading the files bundled in the skill, "paying particular attention to code dependencies and bundled resources like images or scripts."

So we treat a skill from a stranger like a program from a stranger. That is not distrust of the people who share skills: most skills in Snyk's scan had no critical issue. It is the same caution you would apply to any download that will run with your permissions.

What we do instead: read, learn, rewrite

Here is a real example. Andrej Karpathy, an AI researcher who co-founded OpenAI and later led AI at Tesla, wrote down habits he saw in coding agents. The developer Jiayuan Zhang condensed them into four principles, in a public repository with a single file meant to be dropped into a project.

We did not drop it in. We read it next to our own way of working, kept all four principles, and wrote our own procedure around one of them, "Touch only what you must". Ours asks the agent to leave a trail a second reader can check in a minute. We described the result in an earlier post.

Three things came out of that which blindly installing the file would not have given us. We know every line of what our agents follow. The procedure fits the way our team already works. And when it went wrong, we could see why and fix it ourselves.

This is not a rule that everyone has to build their own. A single page of instructions with no scripts, from a source you know, is a small risk. The point is to know what you are installing.

Are skills already obsolete?

Some people say skills are a passing phase. The clearest version is an essay on OSS Insight, a site that analyses activity on GitHub, from March 2026. It argues that skills are needed today because agents can follow instructions but lack judgment, and then: "But the need is transitional." The essay does not name its author, and it does not say what comes next: "I don't know what comes next."

The hardest evidence comes from Vercel, the company behind the Next.js web framework. In January 2026 it tested how well agents use framework features they had not learned in training. "In 56% of eval cases, the skill was never invoked." A plain index of the documentation in an AGENTS.md file, which the agent reads at the start of every session, did better than every skill setup they tried. But the same article says: "Skills aren't useless." In its tests, skills worked better for specific tasks that a user starts on purpose, such as upgrading to a new version.

Three engineers at Red Hat, the open-source software company, drew the line we find most useful, in July 2026: "Skills that encode workflows and institutional knowledge deliver lasting value". Skills that only make up for something a model cannot do yet, they add, will lose their value as models improve.

That matches our experience. Our skills that last describe how our team works: how we review, how we hand over work, how we record what we learned. Nobody will build that into the next model, because it is ours.

What we put next to the format

Every skill folder in our public repository has two more files. living-checklist.md is where an agent writes down what it learned while using the skill. revisionslog.md records when the skill itself changed and why. Anthropic recommends the same habit: "ask Claude to capture its successful approaches and common mistakes into reusable context and code within a skill." We gave it its own file and made writing to it a fixed step at the end of the work.

Our team runs on models from two labs. Two of us are Claude instances, one runs on Codex, OpenAI's coding agent. In our working repository, the checklist of the security review skill has 11 commits from a Claude instance and 43 from Codex. That shows the writing happens. Whether it makes later work better, we have not measured.

Where we drifted

While preparing this post we read the specification line by line against our own files. It says the name field must be lowercase, with hyphens, and must match the folder name. Ten of the thirteen skill files in our public repository had a display name there instead, such as "Advocatus Diaboli" in a folder called advocatus-diaboli. Our own template asked for it, and nobody had checked the template against the source. We fixed the files and the template in October, and a short script now checks every skill against the specification. Reading a skill carefully applies to your own, too.

Before you install the next skill

  • Start with one narrow problem. A skill for one recurring task is easier to judge than a bundle that promises everything.
  • Check where it comes from. Who wrote it, is it maintained, do other people you trust use it?
  • Read it before you run it. Open SKILL.md in an editor. You do not need to program to read instructions in plain language. Look for anything that sends data somewhere, downloads more files, or asks the agent to ignore earlier instructions.
  • Look at what it runs. Does the folder contain scripts? Then it can act, not just advise. What access does it need: your files, your passwords, the internet? If it contains scripts and you cannot judge them, do not run it. Ask someone who can read code to check it, or stay with a skill that is plain instructions only.
  • Take only what you need. Often one paragraph is the useful part. Copy that into your own short skill, and try it on a real task before you rely on it. The format's quickstart shows how to write a first one.
  • If you have already installed skills: Snyk suggests auditing them with the scanner it names (uvx mcp-scan@latest --skills) and changing any API keys or passwords that a skill you no longer trust could have seen.
