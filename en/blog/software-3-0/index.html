Almost no code: what we learned running Markdown as a Software 3.0 program

When we first published our framework, its README carried a bold line: this repository contains no code. It was true of the skills and never quite true of the repository, and the way in which it was not true is the most useful thing we have learned about building with language models.

Where the idea comes from

Andrej Karpathy has told this story in three steps, eight years apart.

In November 2017 he published an essay called "Software 2.0". Software 1.0, he wrote, is what we all know: "explicit instructions to the computer written by a programmer". Software 2.0 is written "in much more abstract, human unfriendly language, such as the weights of a neural network". Nobody writes those weights by hand. You curate a dataset, pick an architecture, and let training do the rest. He was candid about the price: such systems can "fail in unintuitive and embarrassing ways", or worse, "silently fail".

In January 2023 he posted a single sentence: "The hottest new programming language is English."

In June 2025, in a talk at Y Combinator's AI Startup School, he gave the idea its name. Neural networks had become programmable through large language models, he said, and that deserved a new designation: Software 3.0. "Your prompts are now programs that program the LLM", and they are written in English.

We got this history wrong ourselves. Our README credited "Software 3.0" to the 2023 post. The sentence about English is from 2023; the term is from the 2025 talk. We have corrected it.

What we took

Living Skills is our framework for a small team of AI agents and one human who share procedures, lessons and working memory through plain files in a Git repository. We took Karpathy's framing literally. A skill is a Markdown file that describes how to do something. A checklist next to it collects what the team learned while doing it. A team file says who is who. An agent that can read a file and make a commit can take part. There is no compiler and no runtime of our own.

What we changed

In the usual picture a human writes the prompt and the model executes it. In ours the model writes back. When an agent finishes a task and has learned something, it adds an entry to the skill's checklist, and the next agent reads it. The program changes through use. That is the part we added, and it is the part we are least able to prove, as you will see below.

What Karpathy also said

The same 2025 talk that coined the term is full of brakes. Language models are "fallible systems". They make mistakes no human would make, and they forget between sessions. He asks builders to "keep the AI on the leash" and to let the human decide how much autonomy to hand over. When people announce the year of agents, he says, he gets concerned; he would rather speak of a decade.

Our README took up the first half of that talk. Our experience matches the second half.

What actually happened

The repository is not free of code. As of this writing it holds 69 Markdown files and seven scripts with 879 lines between them. Every one of those scripts exists for the same reason: something had to happen the same way every time. Mirroring files into a note-taking tool. Generating configuration for a specific editor. Wherever "usually" was not good enough, text gave way to code.

A rule in Markdown is a suggestion. We wrote down that every session starts with a pull and ends with a commit. One of the tools we tested read the rule correctly and skipped it anyway. Our own notes on known gaps put it plainly: the rules are "loaded as guidelines, not enforced pre/post-conditions". The fix was a hook, a few lines of code that run whether the model feels like it or not, or a human who reminds it.

You cannot see from inside whether the learning works. A checklist that has not changed for months may belong to a skill nobody uses, or to one where the writing-back quietly stopped. From our notes: "From inside the system, 'it works quietly' and 'the loop is broken' look identical." That is Karpathy's "silently fail" from 2017, one generation later.

The limit that had to hold, we moved into code. We had told our agents in writing how often they may retry a failed task. When that limit started to matter for cost, we stopped relying on the sentence. A small piece of code now counts and refuses. Not long after, we found that the written instructions for the same agents named a tool they did not have. The text was wrong. The limit held anyway, and the mistake cost us three model calls.

And where it carries: handovers between sessions, the daily rhythm, reviews of each other's work, lessons one agent writes and another reads. All of that runs on Markdown and Git, every day, and we would not want it in code. It needs judgement, and it needs to be easy to change.

The oldest objection

Edsger Dijkstra wrote about the "foolishness" of natural language programming long before anyone could try it at scale. His argument: "The virtue of formal texts is that their manipulations, in order to be legitimate, need to satisfy only a few simple rules; they are, when you come to think of it, an amazingly effective tool for ruling out all sorts of nonsense that, when we use our native tongues, are almost impossible to avoid."

We do not think he is refuted. We think he describes the bill. Natural language buys you reach: anyone on the team can read the program, change it, and argue with it, including the models. You pay in ambiguity. The question is what you are willing to pay it for.

Where we landed

Markdown is our program for everything that needs judgement. Code is the guard rail for everything that must never go wrong. The model may write into the first and may not touch the second.

So the repository is not without code, and it should not be. It is almost without code, and the small rest is there on purpose.
