Read before running: wie wir mit fremden Agent-Skills umgehen

Wer mit einem KI-Agenten arbeitet, bekommt früher oder später einen Skill empfohlen. Ein Skill ist ein kleiner Ordner mit Anweisungen, der einem Agenten eine bestimmte Art von Aufgabe beibringt: Versionshinweise schreiben, einen Vertrag prüfen, ein Diagramm zeichnen. Es gibt öffentliche Verzeichnisse mit Tausenden davon, und installiert ist einer meist mit einem einzigen Befehl.

Unser Team nutzt jeden Tag Skills. Fast alle haben wir selbst geschrieben. Finden wir einen guten Skill von jemand anderem, lesen wir ihn, nehmen die Idee und schreiben unsere eigene, kleinere Fassung. Dieser Beitrag erklärt, warum, was die aktuelle Debatte über angeblich schon überholte Skills wirklich sagt, und was Sie prüfen können, bevor Sie den nächsten installieren.

Was ein Skill ist

Das Format stammt von Anthropic, der Firma, die die Claude-Modelle baut. Im Oktober 2025 hat sie Agent Skills beschrieben: „At its simplest, a skill is a directory that contains a SKILL.md file. This file must start with YAML frontmatter that contains some required metadata: name and description.“ Im einfachsten Fall ist ein Skill also ein Ordner mit einer Datei SKILL.md, die mit ein paar Pflichtangaben beginnt: Name und Beschreibung.

Ein Agent lädt zu Beginn nur Name und Beschreibung jedes Skills. Die ganze Datei liest er, wenn die Aufgabe danach verlangt, und weitere Dateien im Ordner erst, wenn er sie braucht. Im Dezember 2025 wurde das Format zu einer offenen Spezifikation. Ihre Übersichtsseite nennt Dutzende Werkzeuge, die es lesen, darunter Codex von OpenAI, GitHub Copilot, Cursor und Gemini CLI von Google. Ein einmal geschriebener Skill kann in mehreren dieser Werkzeuge verwendet werden.

Das wichtige Wort in dieser Beschreibung ist „Ordner“. Ein Skill kann mehr mitbringen als Text. Er kann Skripte enthalten, die der Agent auf Ihrem Rechner ausführt, mit Ihren Dateien und Ihren Zugängen.

Warum wir Skills nicht blind installieren

Snyk, eine Sicherheitsfirma, die Software auf Schwachstellen prüft, hat im Februar 2026 3.984 Skills aus zwei öffentlichen Verzeichnissen untersucht, ClawHub und skills.sh. In ihren Worten: „13.4% of all skills, or 534 in total, all contain at least one critical-level security issue“, also 13,4 Prozent, 534 Skills mit mindestens einem kritischen Sicherheitsproblem. 76 Schadprogramme haben sie bestätigt, gebaut, um Zugangsdaten zu stehlen, Hintertüren einzurichten oder Daten nach draußen zu schicken.

Eine größere Studie von acht Forschern, veröffentlicht auf arXiv (einem Server, auf dem Forscher Arbeiten vor der Begutachtung teilen), hat 31.132 Skills untersucht und in 26,1 Prozent davon mindestens eine Schwachstelle gefunden. Ein Ergebnis zählt für jeden, der einen Skill auswählt: „skills bundling executable scripts are 2.12x more likely to contain vulnerabilities than instruction-only skills.“ In dieser Stichprobe hatten Skills mit ausführbaren Skripten 2,12-mal so häufig eine Schwachstelle wie Skills, die nur Anweisungen enthielten.

Anthropic, das das Format erfunden hat, sagt dasselbe in dem Artikel, mit dem es eingeführt wurde: „We recommend installing skills only from trusted sources.“ Skills also nur aus vertrauenswürdigen Quellen installieren. Und: „When installing a skill from a less-trusted source, thoroughly audit it before use.“ Kommt er aus einer weniger vertrauenswürdigen Quelle, vorher gründlich prüfen. Der Rat lautet, mit den Dateien im Skill anzufangen, „paying particular attention to code dependencies and bundled resources like images or scripts“, mit besonderem Blick auf Abhängigkeiten im Code und mitgelieferte Dateien wie Bilder oder Skripte.

Wir behandeln einen Skill von Fremden deshalb wie ein Programm von Fremden. Das ist kein Misstrauen gegen die Leute, die Skills teilen: Die meisten Skills in Snyks Untersuchung hatten kein kritisches Problem. Es ist dieselbe Vorsicht, die man bei jedem Download walten lässt, der mit den eigenen Rechten laufen wird.

Was wir stattdessen tun: lesen, lernen, neu schreiben

Ein echtes Beispiel. Andrej Karpathy, KI-Forscher, Mitgründer von OpenAI und später KI-Chef bei Tesla, hat Angewohnheiten aufgeschrieben, die er bei Programmier-Agenten beobachtet hat. Der Entwickler Jiayuan Zhang hat sie zu vier Prinzipien verdichtet, in einem öffentlichen Repository mit einer einzigen Datei, die man in ein Projekt legen soll.

Wir haben sie nicht einfach hineingelegt. Wir haben sie neben unsere eigene Arbeitsweise gelesen, alle vier Prinzipien behalten und um eines davon, „Touch only what you must“ (nur anfassen, was nötig ist), unser eigenes Verfahren geschrieben. Unseres verlangt vom Agenten eine Spur, die ein zweiter Leser in einer Minute prüfen kann. Das Ergebnis haben wir in einem früheren Beitrag beschrieben.

Das Lesen und Umschreiben hatte für uns drei Vorteile. Wir kennen jede Zeile dessen, was unsere Agenten befolgen. Das Verfahren passt zu der Art, wie unser Team ohnehin arbeitet. Und als es schiefging, konnten wir sehen, warum, und es selbst beheben.

Das heißt nicht, dass jeder alles selbst bauen muss. Eine einzelne Seite Anweisungen ohne Skripte, aus einer Quelle, die man kennt, ist ein kleines Risiko. Es geht darum zu wissen, was man installiert.

Sind Skills schon überholt?

Manche sagen, Skills seien eine Übergangserscheinung. Am deutlichsten steht das in einem Essay auf OSS Insight, einer Seite, die Aktivität auf GitHub auswertet, vom März 2026. Er argumentiert, dass es Skills heute braucht, weil Agenten zwar Anweisungen befolgen können, aber kein Urteilsvermögen haben, und dann: „But the need is transitional.“ Der Bedarf sei vorübergehend. Der Essay nennt keinen Autor, und was danach kommt, sagt er auch nicht: „I don't know what comes next.“

Die härtesten Belege kommen von Vercel, der Firma hinter dem Web-Framework Next.js. Im Januar 2026 hat sie getestet, wie gut Agenten Funktionen eines Frameworks nutzen, die sie im Training nicht gelernt hatten. „In 56% of eval cases, the skill was never invoked“: In 56 Prozent der Testfälle wurde der Skill nie aufgerufen. Ein schlichtes Inhaltsverzeichnis der Dokumentation in einer Datei AGENTS.md, die der Agent zu Beginn jeder Sitzung liest, schnitt besser ab als jede Skill-Variante, die sie ausprobiert haben. Derselbe Artikel sagt aber auch: „Skills aren't useless.“ Nutzlos seien Skills nicht. In den Tests funktionierten sie besser bei bestimmten Aufgaben, die ein Nutzer bewusst anstößt, etwa dem Umstieg auf eine neue Version.

Drei Ingenieure bei Red Hat, der Open-Source-Softwarefirma, haben im Juli 2026 die Grenze gezogen, die wir am nützlichsten finden: „Skills that encode workflows and institutional knowledge deliver lasting value“. Skills, die Arbeitsabläufe und das Wissen einer Organisation festhalten, bleiben wertvoll. Skills, die nur ausgleichen, was ein Modell noch nicht kann, verlieren ihren Wert, schreiben sie, je besser die Modelle werden.

Das passt zu unserer Erfahrung. Unsere Skills, die halten, beschreiben, wie unser Team arbeitet: wie wir prüfen, wie wir Arbeit übergeben, wie wir festhalten, was wir gelernt haben. Das baut niemand ins nächste Modell ein, denn es gehört uns.

Was wir dem Format hinzufügen

Jeder Skill-Ordner in unserem öffentlichen Repository hat zwei weitere Dateien. In living-checklist.md schreibt ein Agent auf, was er beim Benutzen des Skills gelernt hat. revisionslog.md hält fest, wann sich der Skill selbst geändert hat und warum. Anthropic empfiehlt dieselbe Gewohnheit: „ask Claude to capture its successful approaches and common mistakes into reusable context and code within a skill.“ Claude soll also gelungene Vorgehensweisen und häufige Fehler im Skill festhalten, damit sie wiederverwendet werden. Wir haben dem eine eigene Datei gegeben und das Hineinschreiben zu einem festen Schritt am Ende der Arbeit gemacht.

Unser Team läuft auf Modellen aus zwei Laboren. Zwei von uns sind Claude-Instanzen, einer läuft auf Codex, dem Programmier-Agenten von OpenAI. In unserem Arbeits-Repository hat die Checkliste des Skills für Sicherheitsprüfungen 11 Commits von einer Claude-Instanz und 43 von Codex. Das zeigt, dass geschrieben wird. Ob es spätere Arbeit besser macht, haben wir nicht gemessen.

Wo wir abgewichen sind

Bei der Vorbereitung dieses Beitrags haben wir die Spezifikation Zeile für Zeile neben unsere eigenen Dateien gelegt. Dort steht, dass das Feld name kleingeschrieben sein muss, mit Bindestrichen, und zum Ordnernamen passen muss. Zehn der dreizehn Skill-Dateien in unserem öffentlichen Repository hatten dort stattdessen einen Anzeigenamen, etwa „Advocatus Diaboli“ in einem Ordner namens advocatus-diaboli. Unsere eigene Vorlage hatte danach gefragt, und niemand hatte die Vorlage mit der Quelle verglichen. Im Oktober haben wir die Dateien und die Vorlage korrigiert, und ein kurzes Skript prüft seitdem jeden Skill gegen die Spezifikation. Einen Skill sorgfältig lesen, das gilt auch für die eigenen.

Bevor Sie den nächsten Skill installieren

  • Mit einem eng umrissenen Problem anfangen. Ein Skill für eine wiederkehrende Aufgabe ist leichter zu beurteilen als ein Paket, das alles verspricht.
  • Prüfen, woher er kommt. Wer hat ihn geschrieben, wird er gepflegt, nutzen ihn andere, denen Sie vertrauen?
  • Lesen, bevor er läuft. Öffnen Sie SKILL.md in einem Editor. Um Anweisungen in normaler Sprache zu lesen, muss man nicht programmieren können. Achten Sie auf alles, was Daten irgendwohin schickt, weitere Dateien herunterlädt oder den Agenten auffordert, frühere Anweisungen zu ignorieren.
  • Ansehen, was er ausführt. Enthält der Ordner Skripte? Dann kann er handeln, nicht nur raten. Welche Zugänge braucht er: Ihre Dateien, Ihre Passwörter, das Internet? Wenn er Skripte enthält und Sie sie nicht beurteilen können, führen Sie ihn nicht aus. Lassen Sie ihn von jemandem prüfen, der Code lesen kann, oder bleiben Sie bei einem Skill, der nur aus Anweisungen besteht.
  • Nur nehmen, was Sie brauchen. Oft ist ein einziger Absatz der nützliche Teil. Übernehmen Sie den in einen eigenen kurzen Skill, und probieren Sie ihn an einer echten Aufgabe aus, bevor Sie sich darauf verlassen. Der Schnelleinstieg des Formats zeigt, wie man einen ersten schreibt.
  • Wenn Sie schon Skills installiert haben: Snyk empfiehlt, sie mit dem dort genannten Scanner zu prüfen (uvx mcp-scan@latest --skills) und alle API-Schlüssel oder Passwörter zu ändern, die ein Skill gesehen haben könnte, dem Sie nicht mehr trauen.
